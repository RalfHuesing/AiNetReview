# Roadmap: Duplicate code candidates

Source of truth: [Konzept.md](Konzept.md). AiNetLinter's token detection implementation and tests are read-only behavioral references; AiNetReview's current contracts take precedence. Complete the points in order. Each implementation point includes focused automated tests, affected current-state documentation when behavior changes, the affected tests and required project gates, verified checkbox closure, and an atomic commit under the repository rules. This roadmap step does not implement the feature.

- [x] **1 — Validate solution-wide source evidence**
  - Intention and scope: Extend `CurrentFindingValidator` so a finding remains anchored in a C# document owned by its representative project, while each evidence item may reference any C# document in the loaded solution. Preserve canonical project-root-relative paths, loaded-snapshot line and snippet checks, finite metrics, unique identities, deterministic ordering, and failure and cancellation behavior.
  - Not in scope: New finding fields, evidence from outside the loaded C# solution, or relaxed representative ownership.
  - Acceptance: Focused validator and runner tests accept cross-project evidence and reject unknown or noncanonical paths, invalid lines or snippets, and evidence that exists only in a changed disk file rather than the loaded snapshot. Invalid findings fail the analysis without a partial result; cancellation still propagates.

- [x] **2 — Collect and cluster eligible method bodies**
  - Intention and scope: Adapt AiNetLinter's body tokenization, deterministic five-token N-grams, inverted-index candidate generation with at least three shared N-grams, Jaccard scoring, and union-find clustering for AiNetReview's immutable solution snapshot. Include executable ordinary methods, constructors, accessors, and local functions with block or expression bodies across production C# projects. Use the shared test-project, generated-document, and generated-symbol classifiers; preserve identifier and literal text and ignore comment and whitespace trivia. Apply a minimum body-token count of 30 by default and form cluster edges only at the selected `exact` (0.95), `near` (0.80), or `fuzzy` (0.65) threshold. Order members deterministically and score each cluster conservatively from its qualifying edges.
  - Not in scope: Structural similarity, drift search, source-comment suppression, result truncation, a live AiNetLinter dependency, or new shared classifier policy.
  - Acceptance: Focused tests adapted from AiNetLinter cover exact, near, fuzzy and rejected pairs; token-count boundaries; comments, whitespace, identifiers and literals; each declaration kind; test and generated exclusions; cross-project members; and transitive clustering. At the exact threshold, a weaker neighbor cannot remove an exact pair. Repeated scans produce the same members, scores, and order, and cancellation or analysis failure yields no successful partial cluster result.

- [x] **3 — Expose duplicate clusters as review findings**
  - Intention and scope: Implement `duplicate-code-candidates` as a stateless `IReviewRule` with validated `minTokens` and `minimumSimilarity` options. Default to 30 and `exact`; keep the remaining algorithm parameters fixed. Emit one finding for every qualifying cluster, anchored at a deterministic representative, with every member's method identity, project-root-relative source location, token count, and linked source-line evidence. Include numeric member count and conservative cluster score, state the effective similarity threshold, and explain that similarity does not prove the methods should be merged. Return an empty `RuleResult` when no cluster qualifies.
  - Not in scope: Analyzer diagnostics, automatic extraction, a defect claim, or a rule-specific report format.
  - Acceptance: Rule tests verify option defaults and invalid values, all three similarity selections, stable finding identity and order, complete cross-project evidence and metrics, the review wording, and an empty result. Findings pass `CurrentFindingValidator` against the loaded solution.

- [x] **4 — Register and publish the production rule**
  - Intention and scope: Register the rule explicitly in `ServiceRegistration.AddAiNetReviewRules`, list it in repository `ainetreview.json`, and update affected `docs/` pages and indexes to describe only verified behavior. Use the existing runner and Markdown writer contracts so each completed audit publishes all current clusters or an empty rule report.
  - Not in scope: Changes to the CLI command shape, report publication model, MCP tools, or AiNetLinter files.
  - Acceptance: Host integration tests check default and configured similarity, linked evidence for every member including cross-project members, complete and empty reports, changed source snapshots on later runs, and no new published run after analysis failure or cancellation. Production registry and repository configuration tests pass. Run affected suites and required project gates, then review the documentation diff.
