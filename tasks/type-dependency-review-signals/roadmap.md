# Roadmap: Solution-wide type dependency review signals

Authority: [approved concept](Konzept.md). Its measurement definitions, selection conditions, failure policy, and non-goals are binding; this roadmap does not change them. Execute the unchecked points in order when [workflow step 4](../../.agents/agent-workflow/04-orchestrierte-umsetzung.md) is invoked. One roadmap file and one final audit are sufficient; there are no separate milestones or leaf files.

For each implementation point, inspect the current owners and applicable repository rules, implement only that slice, verify it, and commit its code, verified current-state documentation, and completed checkbox together. Keep short validation evidence under the corresponding point: commands/results and material limitations. Use the [documented build/test scripts](../../docs/development/build-and-tests.md); no routine performance gate is added. Do not mark work complete based only on a plan or an unrun check.

- [ ] **4 — Audit the implementation and the usefulness of the generated findings.**
  - Intention: Determine whether the two implemented signals produce accurate, concrete additional review questions with acceptable noise, as required by the [concept's verification and audit contract](Konzept.md#verification-and-audit-of-the-findings).
  - Scope: Use a read-only audit agent to inspect the completed implementation, registrations/options, reporting/baseline behavior, and test evidence against the concept. Generate a fresh audit of this repository with the built production CLI and root configuration, ensuring both new analyses are enabled; for example, after the successful build run `dotnet run --project src/AiNetReview/AiNetReview.csproj --no-build -- review .` from the repository root. Inspect the complete `all-findings` reports for both new analyses even when a baseline exists. Review every finding from these two analyses against its source, relevant users/contracts, and existing signals; inspect positive, negative, and acceptable-design fixture cases as well. Other analyses' reports provide context and do not expand this into a full audit of every existing finding.
  - Non-goals: No production edits by the audit agent, benchmark project, historical data collection, threshold lowering to manufacture findings, automatic refactoring, or repeated audit/correction loop.
  - Acceptance: Record concise evidence here: generated run ID/report path, enabled analyses/effective options, observed review execution time, finding counts and IDs with concrete source-backed classifications, recurring noise patterns, additional useful review questions, and material coverage limitations. For an analysis with no real findings, explicitly state that runtime operation and fixture behavior were verified but practical usefulness on real findings was not demonstrated. Do not claim usefulness from correct measurement alone or promise token/maintenance/error improvements.
  - Completion: Evaluate the audit feedback under workflow step 4. Use at most its one correction implementer for defects that preserve the approved concept, with affected tests and a verified commit. Record any unresolved blocker; a requested change to graph semantics, selection, or scope requires a new concept decision rather than silent tuning. Mark the audit point complete only when the review evidence and correction outcome are recorded and no implementation blocker is concealed. Store the outcome in this roadmap; no separate log or audit file is needed.
