## Finding candidate A-001 — missing-test graph drops reachable calls from FastTests into Core

**Priority P1; confidence high for the observed supported solution.** `MissingTestEvidenceSemanticGraphBuilder` creates one graph node per normalized method symbol in the source solution (`MissingTestEvidenceSemanticGraphBuilder.cs:23, 90-113`). Its `GraphCollector.AddEdge` then requires `nodes.TryGetValue(Normalize(target), out targetNode)` (`:334-345`). That lookup uses `SymbolEqualityComparer.Default`, as does the node dictionary. In the loaded repository solution, a call target obtained from `AiNetReview.FastTests` has the same Core assembly identity, documentation ID, and source file location as the Core node, but symbol equality and containing-type equality are false. The edge is silently discarded. Calls from `AiNetReview.IntegrationTests` to Core are present, so the finding is scoped to the demonstrated FastTests→Core reference context, not every project boundary.

The signal report `audit-reporting/20261003T204611Z-69b83ba6/production/missing-test-evidence-candidates.md:30-40` reports `CodeLineMetrics.CountExecutableDeclaration` (13 decisions), `BelongsToTypePart`, and the private `CountTokenStartLines(IEnumerable<SyntaxToken>)` at line 81 as having no static test path. The source includes recognized `[Fact]` roots that directly call `CountExecutableDeclaration`, for example `tests/AiNetReview.FastTests/Analysis/CodeLineMetricsTests.cs:66-86, 90-112, 116-135, 139-161, 165-185`. AiNetCodeNavigator's complete depth-1 reference query found 19 call sites to `CountExecutableDeclaration`, including those direct calls. Tests also call `CountOwnTypePart` and the public `CountTokenStartLines(SyntaxNode)` overload; those methods call the reported private helpers within Core (`src/AiNetReview.Core/Analysis/CodeLineMetrics.cs:10-15, 47-53, 81-95`). The public overload itself is not a signal finding.

I reproduced the loss against the actual `AiNetReview.slnx` using a disposable reflection probe under this audit directory. The graph has 1,247 nodes and 3,098 edges, including the CodeLineMetrics test roots and Core methods, but zero FastTests→Core edges (and zero FastTests→CodeLineMetrics edges). Other cross-project edges are present: 197 IntegrationTests→Core, 44 IntegrationTests→host, 12 host→Core, and 107 IntegrationTests→TestKit. A separate symbol comparison confirms the FastTests call target and graph node show identical assembly identity (`AiNetReview.Core, Version=1.0.0.0`), declaration ID and source location, while `SymbolEqualityComparer.Default.Equals` is false; the parameter type compares equal. In the IntegrationTests→Core comparison, the corresponding `ReviewRunner.RunAsync` method symbol compares equal. The reproducible graph probe source is `GraphEdgeProbe/Program.cs` and `GraphEdgeProbe/GraphEdgeProbe.csproj`, with output in `graph-edges-probe.log`; the symbol comparison source/output are `Program.cs`, `GraphProbe.csproj`, and `symbol-compare.log`. The prior `graph-probe-cross.log` is retained as an earlier successful output, but the new probe now reproduces those counts from its saved source. The original and fresh-copy generated report both show the affected candidate output; the fresh-copy recheck was performed by the parent auditor.

The causal chain is direct: operation walking recognizes invocations (`MissingTestEvidenceSemanticGraphBuilder.cs:383-388`), but target lookup fails for the cross-context symbol; the resulting graph omits the test path; `MissingTestEvidencePathClassifier` classifies the production candidate as `NoPath`; the analysis emits a false missing-test candidate even though the test calls it. Existing graph tests use `AdhocWorkspace` project references and do not characterize this repository's failing MSBuildWorkspace/FastTests path. The priority reflects false review guidance in the production analysis output and a gap in the very tests intended to validate that guidance; this does not imply that all 171 findings share the same cause.

**Change intention and preservation.** Resolve a bound call to the unique loaded source declaration across compilation contexts, with project/reference provenance and an explicit ambiguity failure or exclusion. The implementation must preserve separate same-named symbols, linked and aliased project ownership, partial methods, generated intermediates, test-vs-production roles, overload selection, method-group uncertainty and virtual/interface uncertainty. Acceptance requires an MSBuildWorkspace-level regression using the actual project-reference shape that proves a direct test call suppresses a finding, a production-only intermediary yields the documented indirect classification, an unrelated method remains `NoPath`, and an ambiguous source owner is never guessed. The existing AdhocWorkspace coverage should remain valid.

## Other concerns checked

- `ControlFlowMetrics` and `MethodControlFlowOutliersAnalysis` agree with their current documented decision definitions, including switch sections/arms, else-if nesting, nested-function exclusion, nearest-rank percentiles and tie handling. Their tests characterize these variants.
- `CodeSizeCandidatesAnalysis` keeps member, type and file populations/options separate and uses independent relative/extreme selection paths. I found no material correctness contradiction in the reviewed selectors or collectors.
- `DeadCodeCandidatesAnalysis` uses solution-wide reference coverage plus uncertainty and recognized indirect bindings; the shared reference index normalizes symbols by assembly identity and declaration ID. Its test-framework helper has stricter metadata assembly checks than the missing-test root classifier. No dead-code false candidate was demonstrated in this pass.
- `TestFrameworkClassifier` identifies framework roots by metadata location and metadata name (`Analysis/TestFrameworkClassifier.cs:124-140`), without checking the defining assembly identity. This may accept a foreign metadata assembly that defines a lookalike `Xunit.FactAttribute` or MSTest/NUnit attribute. Source lookalikes are rejected and current fixtures rely on synthetic metadata identities. I did not demonstrate a real loaded-project false root, so this remains an unverified concern; next check should add a foreign-assembly fixture and compare against the framework identity rules already used by dead-code classification.
- `DuplicateCodeDetector` intentionally forms connected components from qualifying Jaccard edges and preserves body tokens. Dense candidate generation may be costly; no independent finding is made here. The structural-duplication scaling investigation is owned by the parent auditor.
- Type-dependency graph ownership, test/generated separation, source witnesses, cycle thresholds and hub counts have focused tests. The cycle selector's Tarjan traversal is recursive, which can exhaust the process stack for a sufficiently deep type graph; no credible repository-scale trigger was measured here, so this is recorded as a scale hypothesis only.
- Forwarding analysis remains project-local and reports only maximal paths meeting the documented thresholds. Its tests cover convergence, cycles, file/type gates and project-role separation.
- I checked whether Unicode escape spelling could hide a non-ASCII identifier. The analyzer's whitelist rejects the backslash in an escape sequence, so this does not produce the suspected false negative; no concern is retained.
