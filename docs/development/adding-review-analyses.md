# Adding a Review Analysis

Implement `IReviewAnalysis` in a dedicated folder under `src/AiNetReview.Core/ReviewAnalyses/`. Each analysis exposes an immutable `ReviewAnalysisDescriptor` with its stable ID, title, positive behavior version, purpose, measurement, review questions, enabled-by-default state, and option descriptors. The descriptor's `DefaultEnabled` value defaults to `true` and is the source of the analysis's enabled state when a configuration omits `enabled`. `DefaultReviewConfigGenerator` writes that enabled state and each declared option default into generated schema version 1 configuration JSON. Analyses may declare a subset of their options as supported test-project overrides; the generator emits these defaults from the same option descriptors, while validation preserves per-option inheritance provenance. An option descriptor supplies its JSON default and validation; configured values are combined with defaults into ordinally sorted `ReviewAnalysisOptions`.

Review analysis IDs are lowercase ASCII slugs: lowercase letters and digits separated by single hyphens, with no leading or trailing hyphen. They are limited to 252 characters so the generated `<analysisId>.md` filename stays within a 255-character path component. Windows device names (`con`, `prn`, `aux`, `nul`, `com1`–`com9`, and `lpt1`–`lpt9`) are rejected.

`ExecuteAsync` receives a `ReviewContext`, resolved `ReviewAnalysisOptions`, and a cancellation token, and returns a `ReviewAnalysisResult` whose findings collection is immutable. The result can also carry project-scoped exclusions and reasons when conservative binding uncertainty suppresses candidate selection. Review analysis implementations must not keep mutable state between runs. The `method-control-flow-outliers` analysis demonstrates this contract and returns current method-level review candidates across production and test projects.

`ReviewContext` provides checked conversion of loaded project and source paths to project-root-relative paths with `/` separators. Use the shared Core source classifier to identify project roles and generated documents, and to exclude generated symbols by attribute. Test-project detection is based on known test framework assembly names and documented project-name/file-path conventions; generated-document detection uses generated path markers and the first five source lines. Size and control-flow analyses apply descriptor-defined test options per project. Other applicable maintenance analyses include both project roles; missing-test-evidence continues to target production functions. Keep role and generated-code checks centralized.

Analyses that need shared type or method usage information can build `SolutionReferenceIndex` from the `ReviewContext`. It covers all C# projects and source-generated documents, preserves production/test and generated-source provenance, distinguishes method groups and containing-type references, and exposes symbol-local unresolved bindings. Index creation fails when a project compilation or document syntax/semantic model cannot be obtained.

Core also provides an internal, stateless `TypeDependencyGraphBuilder` for direct dependencies between explicitly declared C# source types in the current solution snapshot. Partial declarations merge per project, nested declarations remain separate nodes, and project identity keeps same-named types in different projects distinct. Generated partial locations are omitted while eligible locations still form the node, and generated-member attributes exclude that member's signatures, initializers, bodies, and nested local-function or lambda operations while preserving eligible members on the containing type. Cross-project source targets resolve through their declaring syntax trees to the loaded owning project; missing or ambiguous source ownership fails instead of selecting a project by assembly identity or documentation ID. The builder combines declaration/signature and explicit type uses with semantically bound member uses, normalizes external generic wrappers to their source type arguments, and keeps one deterministic source witness per pair and evidence kind. Adjacency drops self-edges and repeated sites. Production relationships and direct test-to-production context are stored separately; generated and metadata targets are excluded, and dynamic targets do not create guessed edges. Missing required compilation, source/semantic models, or static bindings fail graph construction with project, source, and position context. The builder adds no cache and is not itself a registered review analysis.

The production registry also includes `DeadCodeCandidatesAnalysis`. Its candidate selection uses direct solution-wide references plus recognized entry-point attributes, reflection, dependency injection, framework and markup bindings from the loaded snapshot. Self-references alone do not count as method usage. It groups an unused type with its methods, includes both production and test projects, skips generated declarations and protects public API by default through the `apiSurface` option. The compiler-selected entry point and its containing-type chain are protected in executable projects, while unused ordinary methods of those types remain candidates; this protection does not depend on API mode. A library `Main` receives no special protection. Metadata-backed xUnit v2/v3, NUnit, and MSTest entry points, fixture types, lifecycle contracts and supported named data-provider bindings are protected. Both legacy Visual Studio Test Platform and current `MSTest.TestFramework` metadata identities are recognized. Attribute recognition uses framework metadata identities, so source-local lookalikes do not count; derived framework attributes, inherited test methods/hooks, skipped tests, and required containing types retain protection. A private ordinary helper beside a protected test remains a candidate. Ambiguous source names make framework-plausible providers uncertain across the known source type and inherited members, including private static enumerable NUnit methods; ordinary void or scalar helpers remain candidates. An unresolved provider type excludes the originating project and its referenced C# dependency area, with project-relative paths and reasons retained in `ReviewAnalysisResult.ScopeExclusions`. Unsupported custom runner bindings remain outside the recognized protection contract and require manual review. It accepts additional fully qualified entry-point attribute names through `entryPointAttributes`; its two fixed framework attributes remain active. Unresolved local bindings suppress only affected candidates, and markup that cannot be evaluated fails the analysis. Findings are recomputed and reported on every audit without source-comment suppressions. Empty results create no analysis report; analysis failure and cancellation do not publish a run.

`IndirectionDriftCandidatesAnalysis` reports maximal statically declared paths of transparent forwarding within one production or test C# project. A path needs at least two forwarding edges and three distinct containing types and source files. It includes every member as ordered evidence and a related symbol, and emits the explanatory edge, type, and file counts. Its dedicated Markdown item preserves call order and labels the path as statically declared; it does not resolve runtime dispatch or measure historical growth. It has no custom options. Empty results create no analysis report; analysis failure and cancellation do not publish a run.

`DuplicateCodeCandidatesAnalysis` reports current clusters of executable methods with similar bodies across production and test C# projects. It uses the loaded source snapshot, keeps generated sources and symbols excluded through the shared classifier while including both project roles, and accepts `minTokens` (default 30) and `minimumSimilarity` (default `exact`; `near` and `fuzzy` are also available). Each finding gives cluster size, similarity against the selected minimum, and every member's identity and source location. Similarity is a review prompt rather than a claim that methods should be merged. A run with no cluster creates no analysis report; analysis failure and cancellation publish no run.

`StructuralDuplicationCandidatesAnalysis` reports exact statement fragments across production and test C# projects after bound local and parameter normalization. It preserves node/token structure, member names, operators, literals, and recursive type distinctions; applies fixed three-statement and 60-token floors; and includes all occurrences in a dedicated Markdown branch. The detector respects executable-owner and binding barriers, selects exact complete groups with containment suppression, and emits all source coordinates for normal changed-file selection. It has no custom options. A run without candidates creates no analysis report; failure and cancellation do not publish a run.

`NonAsciiIdentifiersAnalysis` inspects production and test C# syntax trees for non-ASCII characters in identifier names across namespaces, types, enum members, methods, properties, fields, parameters, and local functions. It skips generated documents through the shared classifier, ignores generic type parameters, comments, string literals, and verbatim `@` prefixes, and declares no custom options. Findings identify the affected element with its identifier name and non-ASCII character details.

The Markdown writer classifies each finding from its subject occurrences into production, tests, or mixed. Keep contextual evidence distinct from finding subjects: for example, a missing-test-evidence candidate remains production-origin even when its shortest resolved path includes test symbols. Preserve those test symbols as related evidence. Keep one canonical finding description with the measurements and evidence needed for review; the writer supplies stable IDs and compact routing. The root report provides the common assignment across all three areas, while view indexes and nonempty reports are published atomically as one immutable run. See [Current findings](../review/findings.md) for the reporting contract.

Register product analyses explicitly through `ServiceRegistration.AddAiNetReviewAnalyses`. `ServiceRegistration.AddAiNetReviewServices` registers the shared `ReviewAnalysisRegistry`. The registry rejects invalid or duplicate analysis IDs and exposes its analyses in ordinal ID order. The integration test project can add its fixture analysis through an explicit test-only DI registration.

`TypeDependencyCycleCandidatesAnalysis` reuses the stateless `TypeDependencyGraphBuilder` and reports maximal production strongly connected components with at least three distinct types across at least three canonical declaration source files. It includes every participating declaration, each internal edge's retained source witnesses, and one deterministic genuine cycle example. Its baseline-backed `changed-files` view uses snapshot-wide C# selection.

`TypeDependencyHubCandidatesAnalysis` reuses the same graph and reports a production type only when its distinct direct production fan-in and fan-out both meet the inclusive `minFanIn` and `minFanOut` thresholds (10 each by default). It lists every production neighbor and retained edge witness, includes all partial subject declarations, and keeps direct test consumers separate from production counts and finding subjects. Neighbor file counts deduplicate canonical declaration paths, including linked files; project counts retain project-specific type nodes. The baseline-backed `changed-files` view shares the snapshot-wide C# selection used by cycle findings.
