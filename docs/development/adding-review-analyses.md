# Adding a Review Analysis

Implement `IReviewAnalysis` in a dedicated folder under `src/AiNetReview.Core/ReviewAnalyses/`. Each analysis exposes an immutable `ReviewAnalysisDescriptor` with its stable ID, title, positive behavior version, purpose, measurement, review questions, enabled-by-default state, and option descriptors. The descriptor's `DefaultEnabled` value defaults to `true` and is the source of the analysis's enabled state when a configuration omits `enabled`. `DefaultReviewConfigGenerator` writes that enabled state and each declared option default into generated schema version 1 configuration JSON. Analyses may declare a subset of their options as supported test-project overrides; the generator emits these defaults from the same option descriptors, while validation preserves per-option inheritance provenance. An option descriptor supplies its JSON default and validation; configured values are combined with defaults into ordinally sorted `ReviewAnalysisOptions`.

Review analysis IDs are lowercase ASCII slugs: lowercase letters and digits separated by single hyphens, with no leading or trailing hyphen. They are limited to 252 characters so the generated `<analysisId>.md` filename stays within a 255-character path component. Windows device names (`con`, `prn`, `aux`, `nul`, `com1`–`com9`, and `lpt1`–`lpt9`) are rejected.

`ExecuteAsync` receives a `ReviewContext`, resolved `ReviewAnalysisOptions`, and a cancellation token, and returns a `ReviewAnalysisResult` whose findings collection is immutable. Review analysis implementations must not keep mutable state between runs. The `method-control-flow-outliers` analysis demonstrates this contract and returns current method-level review candidates across production and test projects.

`ReviewContext` provides checked conversion of loaded project and source paths to project-root-relative paths with `/` separators. Use the shared Core source classifier to identify project roles and generated documents, and to exclude generated symbols by attribute. Test-project detection is based on known test framework assembly names and documented project-name/file-path conventions; generated-document detection uses generated path markers and the first five source lines. Size and control-flow analyses apply descriptor-defined test options per project. Other applicable maintenance analyses include both project roles; missing-test-evidence continues to target production functions. Keep role and generated-code checks centralized.

Analyses that need shared type or method usage information can build `SolutionReferenceIndex` from the `ReviewContext`. It covers all C# projects and source-generated documents, preserves production/test and generated-source provenance, distinguishes method groups and containing-type references, and exposes symbol-local unresolved bindings. Index creation fails when a project compilation or document syntax/semantic model cannot be obtained.

The production registry also includes `DeadCodeCandidatesAnalysis`. Its candidate selection uses direct solution-wide references plus recognized entry-point attributes, reflection, dependency injection, framework and markup bindings from the loaded snapshot. Self-references alone do not count as method usage. It groups an unused type with its methods, skips generated declarations and non-production projects, and protects public API by default through the `apiSurface` option. The compiler-selected entry point and its containing-type chain are protected in executable projects, while unused ordinary methods of those types remain candidates; this protection does not depend on API mode. A library `Main` receives no special protection. It accepts additional fully qualified entry-point attribute names through `entryPointAttributes`; its two fixed framework attributes remain active. Unresolved local bindings suppress only affected candidates, and markup that cannot be evaluated fails the analysis. Findings are recomputed and reported on every audit without source-comment suppressions. Empty results create no analysis report; analysis failure and cancellation do not publish a run.

`IndirectionDriftCandidatesAnalysis` reports maximal statically declared paths of transparent forwarding within one production C# project. A path needs at least two forwarding edges and three distinct containing types and source files. It uses the shared source classifier, includes every member as ordered evidence and a related symbol, and emits the explanatory edge, type, and file counts. Its dedicated Markdown item preserves call order and labels the path as statically declared; it does not resolve runtime dispatch or measure historical growth. It has no custom options. Empty results create no analysis report; analysis failure and cancellation do not publish a run.

`DuplicateCodeCandidatesAnalysis` reports current clusters of executable methods with similar bodies across production C# projects. It uses the loaded source snapshot, skips generated and test sources through the shared classifier, and accepts `minTokens` (default 30) and `minimumSimilarity` (default `exact`; `near` and `fuzzy` are also available). Each report row gives cluster size and similarity against the selected minimum and links to all cluster members. Similarity is a review prompt rather than a claim that methods should be merged. A run with no cluster creates no analysis report; analysis failure and cancellation publish no run.

`StructuralDuplicationCandidatesAnalysis` reports exact statement fragments after bound local and parameter normalization. It preserves node/token structure, member names, operators, literals, and recursive type distinctions; applies fixed three-statement and 60-token floors; and includes all occurrences in a dedicated Markdown branch. The detector respects executable-owner and binding barriers, selects exact complete groups with containment suppression, and emits all source coordinates for normal changed-file selection. It has no custom options. A run without candidates creates no analysis report; failure and cancellation do not publish a run.

`NonAsciiIdentifiersAnalysis` inspects production C# syntax trees for non-ASCII characters in identifier names across namespaces, types, enum members, methods, properties, fields, parameters, and local functions. It skips test projects and generated documents through the shared classifier, ignores generic type parameters, comments, string literals, and verbatim `@` prefixes, and declares no custom options. Findings identify the affected element with its identifier name and non-ASCII character details.

Register product analyses explicitly through `ServiceRegistration.AddAiNetReviewAnalyses`. `ServiceRegistration.AddAiNetReviewServices` registers the shared `ReviewAnalysisRegistry`. The registry rejects invalid or duplicate analysis IDs and exposes its analyses in ordinal ID order. The integration test project can add its fixture analysis through an explicit test-only DI registration.
