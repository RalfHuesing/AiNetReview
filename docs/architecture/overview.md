# Architecture

The solution has five projects: Core, the executable host, TestKit, FastTests, and IntegrationTests. Core owns configuration validation, MSBuild/Roslyn solution loading, shared production/test and generated-source classification, checked project-root-relative path conversion, analysis descriptors and registration, the analysis runner, and finding models. The host composes Core services and initializes logging. TestKit is independent of Core; FastTests reference Core and TestKit; IntegrationTests reference Core, host, and TestKit.

The Core does not reference the host. The host is the composition root. Product analyses are registered explicitly; the production registry contains `code-size-candidates`, `method-control-flow-outliers`, `dead-code-candidates`, `duplicate-code-candidates`, `indirection-drift-candidates`, `missing-test-evidence-candidates`, `non-ascii-identifiers`, `structural-duplication-candidates`, and `type-dependency-cycle-candidates`. The structural analysis detects exact statement fragments after local and parameter normalization and retains type, operator, literal, and member-name differences. The current dependency direction and package references are listed in [Dependencies](dependencies.md).

Core opens `.sln` and `.slnx` files through `MSBuildWorkspace`, checks C# source paths against the project and output directories, and materializes every C# document's text into the returned immutable Roslyn `Solution`. Generated external source included by test projects is removed before the boundary check. When `dead-code-candidates` is configured, Core also captures `.razor`, `.xaml`, and `.js` files under each analyzed project root into the loaded snapshot. Discovery does not follow reparse-point paths and skips standard or project-configured build output and intermediate directories, dependency and generated-content directories, and nested projects. Additional-document paths are validated against the project boundary but enter the snapshot only through safe filesystem discovery. Unreadable files and the 2,000-file or 1 MiB per-file limits fail the analysis. Other configurations do not scan markup files. The shared source snapshot excludes generated C# documents, includes all remaining C# documents, and adds captured markup files when configured; it hashes file bytes as lowercase SHA-256 once per loaded solution. It creates and checks each C# project's compilation before handing the solution to the analysis runner. A solution without a C# project, an incomplete load, or a compiler error fails the analysis; warnings promoted to errors by the target build policy do not block review.

The dead-code analysis keeps C# semantic analysis in `DeadCodeIndirectUsageIndex` and delegates XAML, Razor, and JavaScript snapshot evaluation to `DeadCodeMarkupUsageCollector`. The collector returns protected and uncertain symbols for the index to combine with C# analysis. Both paths share source-type enumeration, symbol tracking, and symbol normalization.

Analyses can build a shared `SolutionReferenceIndex` from the loaded context. It indexes semantically bound C# type and method references across production and test projects, including source-generated documents, and records whether a use is a method group, comes from generated code, or is a self-reference. A missing compilation or unavailable syntax/semantic model fails index creation; unresolved candidate bindings are recorded as uncertainty for the affected symbol. An empty reference list with no such uncertainty represents complete zero-reference coverage.

After validating findings, the reporting path derives the existing `changed-files` selection and complete `all-findings` set from validated findings. It preserves each finding's stable ID, project/source identity, occurrence locations, and roles. `MarkdownReportWriter` writes the compact `audit-map/all-findings/index.md` for every run and adds `audit-map/changed-files/index.md` only when a baseline exists. The maps group findings by project and representative source file and link to their original report anchors. It does not prepare map-only semantic reference context or separate package/detail/navigation pages. The indexes are published with the existing atomic report-directory rename.

The host exposes the `review [project-path]` and `baseline [project-path]` commands. Both use `ainetreview.json` from the selected project root, create it from a discovered solution when it is missing, validate the configuration, and load the source snapshot. Baseline writes the snapshot's project-relative SHA-256 records directly to `baseline.json` without invoking review analyses. The CLI adapter is injectable for streams and service providers; the production composition root registers `code-size-candidates`, `method-control-flow-outliers`, `dead-code-candidates`, `duplicate-code-candidates`, `indirection-drift-candidates`, `missing-test-evidence-candidates`, `non-ascii-identifiers`, `structural-duplication-candidates`, and `type-dependency-cycle-candidates`. Review connects the configuration validator, solution loader, review runner, and Markdown report writer, returning one JSON process response only after publication succeeds. The host initializes executable-relative Serilog before parsing. See [CLI](../interfaces/cli.md) for command and logging contracts.
