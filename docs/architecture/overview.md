# Architecture

The solution has five projects: Core, the executable host, TestKit, FastTests, and IntegrationTests. Core owns configuration validation, MSBuild/Roslyn solution loading, shared production/test and generated-source classification, checked project-root-relative path conversion, analysis descriptors and registration, the analysis runner, and finding models. The host composes Core services and initializes logging. TestKit is independent of Core; FastTests reference Core and TestKit; IntegrationTests reference Core, host, and TestKit.

The Core does not reference the host. The host is the composition root. Product analyses are registered explicitly; the production registry contains `method-control-flow-outliers`, `dead-code-candidates`, and `duplicate-code-candidates`. The current dependency direction and package references are listed in [Dependencies](dependencies.md).

Core opens `.sln` and `.slnx` files through `MSBuildWorkspace`, checks C# source paths against the project and output directories, and materializes every C# document's text into the returned immutable Roslyn `Solution`. Generated external source included by test projects is removed before the boundary check. When `dead-code-candidates` is configured, Core also captures `.razor`, `.xaml`, and `.js` files under each analyzed project root into the loaded snapshot. Discovery does not follow reparse-point paths and skips standard or project-configured build output and intermediate directories, dependency and generated-content directories, and nested projects. Additional-document paths are validated against the project boundary but enter the snapshot only through safe filesystem discovery. Unreadable files and the 2,000-file or 1 MiB per-file limits fail the analysis. Other configurations do not scan markup files. The shared source snapshot excludes generated C# documents, includes all remaining C# documents, and adds captured markup files when configured; it hashes file bytes as lowercase SHA-256 once per loaded solution. It creates and checks each C# project's compilation before handing the solution to the analysis runner. A solution without a C# project, an incomplete load, or a compiler error fails the analysis; warnings promoted to errors by the target build policy do not block review.

The dead-code analysis keeps C# semantic analysis in `DeadCodeIndirectUsageIndex` and delegates XAML, Razor, and JavaScript snapshot evaluation to `DeadCodeMarkupUsageCollector`. The collector returns protected and uncertain symbols for the index to combine with C# analysis. Both paths share source-type enumeration and symbol normalization.

Analyses can build a shared `SolutionReferenceIndex` from the loaded context. It indexes semantically bound C# type and method references across production and test projects, including source-generated documents, and records whether a use is a method group, comes from generated code, or is a self-reference. A missing compilation or unavailable syntax/semantic model fails index creation; unresolved candidate bindings are recorded as uncertainty for the affected symbol. An empty reference list with no such uncertainty represents complete zero-reference coverage.

The host exposes the `review --config` flow and the independent `--cmd baseline` operation. Both validate the configuration, load the same source snapshot, and compute one project-relative SHA-256 record per source file; baseline writes those records directly to `baseline.json` without invoking review analyses. The CLI adapter is injectable for streams and service providers; the production composition root registers `method-control-flow-outliers`, `dead-code-candidates`, and `duplicate-code-candidates`. Review connects the configuration validator, solution loader, review runner, and Markdown report writer, returning one JSON process response only after publication succeeds. The host initializes executable-relative Serilog before parsing. See [CLI](../interfaces/cli.md) for command and logging contracts.
