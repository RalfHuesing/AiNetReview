# Current findings

`IReviewRule.ExecuteAsync` returns a `RuleResult` containing immutable `FindingDraft` values. A draft currently carries project and source paths, a subject ID, discriminator, starting line, rationale, numeric metrics, and evidence entries. It contains no snapshot, comparison text, fingerprint, or source-file hash list.

`ReviewRunner` invokes the configured rules in ordinal rule-ID order and returns each rule's current result. It validates each draft against the loaded C# project and document paths and source text, including one-based line bounds, finite metrics, required evidence, and unique per-run identity tuples. A finding's representative source must belong to its declared project; evidence may point to any loaded C# document in the solution. Evidence snippets must occur on their referenced loaded snapshot line. Findings are sorted by project path, source path, start line, subject ID, and discriminator. It retains no result between calls. Rule exceptions and invalid findings fail the whole analysis; cancellation propagates without returning a partial result.

`MarkdownReportWriter` writes UTF-8 Markdown with LF line endings. The index contains the run ID, absolute project root, relative solution path, links only to rules with findings, and instructions for removing handled rows and files. An active audit with no findings says `No findings were found`; an audit with no active rules says `No review was performed because all rules are disabled`. Neither case creates rule files. When the final finding is handled, the agent replaces the work instructions with `All findings addressed`. Each nonempty rule report shows its purpose, effective options, review questions, and one editable table row per finding in `Source`, `Signal`, and `Other Locations` columns. Rows link to a representative source location and any additional source locations. Output omits raw metrics, long rationale text, and code snippets. Rules, findings, options, and evidence have deterministic ordering; Markdown text is escaped and source links use encoded relative path segments. Each report set is assembled in a unique temporary directory and published by renaming that directory to its UTC timestamp and random run ID. A handled pre-publication failure removes its temporary directory, and successful runs leave older reports unchanged.

The production registry contains `method-control-flow-outliers`, `dead-code-candidates`, and `duplicate-code-candidates`. The first rule compares executable method declarations within each production C# project. It uses the nearest-rank percentile selected by the `percentile` option (default 90), with minimum cutoffs of 8 decisions and 4 nested decisions. Ties at the cutoff are included, so the report does not hide methods sharing a boundary value.

The rule analyzes production C# projects only. The shared Core source classifier identifies test projects from known test-framework reference assembly names (`xunit`, `nunit`, `mstest`, and Microsoft TestPlatform families), common project-name or project-file suffixes (`Tests`, `Test`, `UnitTests`, `UnitTest`, `IntegrationTests`, `IntegrationTest`, `FastTests`, `ComponentTests`, `TestKit`, `Specs`, and `Spec`), or exact test directory segments (`tests`, `test`, `unittests`, `integrationtests`, `fasttests`, `componenttests`, `testkit`, `specs`, and `spec`). Suffix matching requires a dotted or uppercase token boundary. These are deterministic conventions; an unusual test project without any of these markers is not inferred to be a test project.

Generated documents are excluded when their path is under `obj` or their filename ends in `.g.cs`, `.g.i.cs`, `.generated.cs`, or `.designer.cs`, or when one of the first five source lines contains `<auto-generated`. Methods are excluded when the method or a containing type has `GeneratedCodeAttribute` or `CompilerGeneratedAttribute`. The classifier reads source text only from the loaded Roslyn solution.

`decisionCount` counts each `if`, switch section (including `default` and grouped labels as one section), switch-expression arm, conditional expression, loop (`for`, `foreach`, `while`, or `do`), and `catch` clause once. `decisionConstructCount` counts each `if`, conditional expression, loop, and `catch` once, and counts an entire switch statement or switch expression once, regardless of its number of sections or arms. `maxDecisionNesting` is the deepest nesting of counted decisions; an `else if` chain remains at the same nesting level. A method is selected when `decisionCount` meets its effective cutoff **and** `decisionConstructCount` is at least 2, or when `maxDecisionNesting` meets its effective cutoff. This keeps a single flat switch from qualifying solely because it has many arms, while retaining methods with multiple separate decisions and deeply nested paths. `sourceSpanLines` gives the inclusive method declaration span as context, not as a selection threshold. Local functions and lambdas are not emitted as separate candidates or added to their containing method's counts.

Each finding includes the method symbol, declaration location, a source snippet identifying the deepest counted decision, raw metric values, project group size, percentile values, effective cutoffs, and descending ranks. The report signal shows the triggered decision or nesting values and their cutoffs. A finding is a review prompt, not a defect claim or a refactoring instruction. `FixtureFindingRule` remains confined to IntegrationTests.

`dead-code-candidates` examines explicit types and ordinary methods in production C# projects. It accounts for solution-wide semantic references, recognized indirect bindings and the captured markup snapshot. A type with no known external use is reported once as a group, so its methods do not appear as separate findings. The default `apiSurface` value, `external_library`, protects publicly visible declarations; `closed_solution` also considers them as candidates. `entryPointAttributes` adds fully qualified attribute type names while the built-in module initializer and JS interop entry point attributes stay active. Each report row links to its declaration and labels it as a type or method without known use. The report asks reviewers to check reflection, dependency injection, framework or markup entry points, and use outside the analyzed solution. Findings are recalculated on every audit; the rule has no source-comment suppression mechanism. An audit with no candidates creates no rule file. Analysis failure or cancellation publishes no run.

`duplicate-code-candidates` compares executable method, constructor, accessor, and local-function bodies in production C# projects using the loaded solution snapshot. Bodies shorter than `minTokens` (default 30) are skipped. The fixed token algorithm preserves identifier and literal text, ignores whitespace and comments, creates deterministic five-token n-grams, and joins pairs that share at least three n-grams and meet the selected Jaccard threshold. `minimumSimilarity` defaults to `exact` (0.95); `near` (0.80) and `fuzzy` (0.65) are explicit lower thresholds. One finding represents each connected cluster formed by qualifying edges and contains every member's project-relative source location, method identity, token count, and linked source-line evidence. Its score is the lowest qualifying edge score in that cluster. Members may come from different projects. Report rows show the cluster size and similarity relative to the selected minimum, and link to every member. Similarity alone does not prove that methods should be merged. Clusters are recomputed for every audit; an audit with no candidates creates no rule file. Analysis failure or cancellation publishes no run.
