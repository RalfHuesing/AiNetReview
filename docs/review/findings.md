# Current findings

`IReviewAnalysis.ExecuteAsync` returns a `ReviewAnalysisResult` containing immutable `FindingDraft` values. A draft currently carries project and source paths, a subject ID, discriminator, starting line, rationale, numeric metrics, and evidence entries. It contains no snapshot, comparison text, fingerprint, or source-file hash list.

`ReviewRunner` invokes the configured analyses in ordinal analysis-ID order and returns each analysis's current result. It validates each draft against the loaded C# project and document paths and source text, including one-based line bounds, finite metrics, required evidence, and unique per-run identity tuples. A finding's representative source must belong to its declared project; evidence may point to any loaded C# document in the solution. Evidence snippets must occur on their referenced loaded snapshot line. Findings are sorted by project path, source path, start line, subject ID, and discriminator. It retains no result between calls. Review analysis exceptions and invalid findings fail the whole analysis; cancellation propagates without returning a partial result.

The host reads the optional `baseline.json` from the resolved output directory before running the analyses. `ReviewRunner` then adds per-finding review metadata while preserving each validated analysis result unchanged: participating source paths include the finding source and every evidence source; `changed-files` selection is true when any participating file is missing from the baseline or has a different SHA-256. With no baseline, every current source file is considered new. A duplicate-code cluster explicitly identifies each member symbol and source location, so a change to any member selects the cluster. Cross-analysis relationships match project path and symbol identity; sharing only a source file does not create a relationship. Related references retain the precise member path and line for clusters.

`MarkdownReportWriter` writes UTF-8 Markdown with LF line endings. The root `index.md` focuses on `changed-files/` as the primary review source, directly links each analysis report that has findings in changed files, demotes `all-findings/` to a reference section with explicit instructions for AI agents not to process it without explicit user direction, and includes review guidance instructing reviewers and agents to work strictly from `changed-files/`. A normal CLI run prints the PowerShell baseline command `<exePath> baseline "<projectRoot>"`, using the `ainetreview.json` and output directory configured in that project root. A centrally hosted manual audit instead prints a command to run `scripts/test-audit.ps1 -Target <name> -BaselineOnly`, which refreshes the central baseline from the selected host-side audit profile without writing config or baseline files to the target repository. Each view has its own `index.md` linking only to analysis files that contain findings in that view; `all-findings/index.md` includes an explicit notice instructing AI agents not to process findings from that view unless requested. With no baseline, every current source file is considered new, so both views contain the same findings. An active audit with no findings says `No findings were found`; an audit with no active analyses says `No review was performed because all analyses are disabled`. Empty views do not create analysis files.

Each nonempty analysis report shows its purpose, effective options, review questions, and a `## Findings` list of review items. Output omits HTML anchors, line numbers, and markdown hyperlinks to eliminate noise and remain stable during refactorings. Single-symbol findings list the repository-relative source path and unambiguous symbol DocId, followed by their review signal and any related analysis IDs. Cluster findings (such as duplicate code) identify the cluster signal and each participating member's source path and symbol DocId. `indirection-drift-candidates` has a dedicated `Forwarding path` item that prints the forwarding edge, distinct type, and distinct file counts, then lists every member's source path and DocId in evidence call order. That order comes from stored evidence, not alphabetic symbol ordering. The `changed-files/` reports are independent copies, so editing them does not modify the complete `all-findings/` view. Output omits raw metrics, long rationale text, and code snippets. Analyses, findings, options, and evidence have deterministic ordering. Each report set, including both views and indexes, is assembled in a unique temporary directory and published by renaming that directory to its UTC timestamp and random run ID. A handled pre-publication failure removes its temporary directory, and successful runs leave older reports unchanged.

The production registry contains `code-size-candidates`, `method-control-flow-outliers`, `dead-code-candidates`, `duplicate-code-candidates`, `indirection-drift-candidates`, `missing-test-evidence-candidates`, and `non-ascii-identifiers`. The first analysis compares executable method declarations within each production C# project. It uses the nearest-rank percentile selected by the `percentile` option (default 90), with minimum cutoffs of 8 decisions and 4 nested decisions. Ties at the cutoff are included, so the report does not hide methods sharing a boundary value.

The analysis analyzes production C# projects only. The shared Core source classifier identifies test projects from known test-framework reference assembly names (`xunit`, `nunit`, `mstest`, and Microsoft TestPlatform families), common project-name or project-file suffixes (`Tests`, `Test`, `UnitTests`, `UnitTest`, `IntegrationTests`, `IntegrationTest`, `FastTests`, `ComponentTests`, `TestKit`, `Specs`, and `Spec`), or exact test directory segments (`tests`, `test`, `unittests`, `integrationtests`, `fasttests`, `componenttests`, `testkit`, `specs`, and `spec`). Suffix matching requires a dotted or uppercase token boundary. These are deterministic conventions; an unusual test project without any of these markers is not inferred to be a test project.

Generated documents are excluded when their path is under `obj` or their filename ends in `.g.cs`, `.g.i.cs`, `.generated.cs`, or `.designer.cs`, or when one of the first five source lines contains `<auto-generated`. Methods are excluded when the method or a containing type has `GeneratedCodeAttribute` or `CompilerGeneratedAttribute`. The classifier reads source text only from the loaded Roslyn solution.

`decisionCount` counts each `if`, switch section (including `default` and grouped labels as one section), switch-expression arm, conditional expression, loop (`for`, `foreach`, `while`, or `do`), and `catch` clause once. `decisionConstructCount` counts each `if`, conditional expression, loop, and `catch` once, and counts an entire switch statement or switch expression once, regardless of its number of sections or arms. `maxDecisionNesting` is the deepest nesting of counted decisions; an `else if` chain remains at the same nesting level. A method is selected when `decisionCount` meets its effective cutoff **and** `decisionConstructCount` is at least 2, or when `maxDecisionNesting` meets its effective cutoff. This keeps a single flat switch from qualifying solely because it has many arms, while retaining methods with multiple separate decisions and deeply nested paths. `sourceSpanLines` gives the inclusive method declaration span as context, not as a selection threshold. Local functions and lambdas are not emitted as separate candidates or added to their containing method's counts.

Each finding includes the method symbol, declaration location, a source snippet identifying the deepest counted decision, raw metric values, project group size, percentile values, effective cutoffs, and descending ranks. The report signal shows the triggered decision or nesting values and their cutoffs. A finding is a review prompt, not a defect claim or a refactoring instruction. `FixtureFindingAnalysis` remains confined to IntegrationTests.

`dead-code-candidates` examines explicit types and ordinary methods in production C# projects. It accounts for solution-wide semantic references, recognized indirect bindings and the captured markup snapshot. A type with no known external use is reported once as a group, so its methods do not appear as separate findings. The default `apiSurface` value, `external_library`, protects publicly visible declarations; `closed_solution` also considers them as candidates. `entryPointAttributes` adds fully qualified attribute type names while the built-in module initializer and JS interop entry point attributes stay active. Each report row links to its declaration and labels it as a type or method without known use. The report asks reviewers to check reflection, dependency injection, framework or markup entry points, and use outside the analyzed solution. Findings are recalculated on every audit; the analysis has no source-comment suppression mechanism. An audit with no candidates creates no analysis file. Analysis failure or cancellation publishes no run.

`duplicate-code-candidates` compares executable method, constructor, accessor, and local-function bodies in production C# projects using the loaded solution snapshot. Bodies shorter than `minTokens` (default 30) are skipped. The fixed token algorithm preserves identifier and literal text, ignores whitespace and comments, creates deterministic five-token n-grams, and joins pairs that share at least three n-grams and meet the selected Jaccard threshold. `minimumSimilarity` defaults to `exact` (0.95); `near` (0.80) and `fuzzy` (0.65) are explicit lower thresholds. One finding represents each connected cluster formed by qualifying edges and contains every member's project-relative source location, method identity, token count, and linked source-line evidence. Its score is the lowest qualifying edge score in that cluster. Members may come from different projects. Report rows show the cluster size and similarity relative to the selected minimum, and link to every member. Similarity alone does not prove that methods should be merged. Clusters are recomputed for every audit; an audit with no candidates creates no analysis file. Analysis failure or cancellation publishes no run.

`non-ascii-identifiers` flags identifier tokens that contain non-ASCII characters in production C# source. It inspects namespaces, types (classes, records, structs, interfaces, and enums), enum members, methods, properties, fields, parameters, local functions, and local variables. Allowed characters for identifiers are `a-z`, `A-Z`, `0-9`, and underscore (namespaces additionally allow dot). Verbatim identifiers with an `@` prefix ignore the `@`. Test projects and generated code or symbols are excluded using the shared Core source classifier. Findings report the declaration's project and source paths, symbol identity, start line, and evidence pointing to the identifier token. The analysis supports only `enabled` (default `true`) without additional options. An audit with no candidates creates no analysis file. Analysis failure or cancellation publishes no run.

`indirection-drift-candidates` reports one candidate for each maximal root path containing at least two transparent forwarding edges, three distinct containing types, and three distinct project-relative C# source files in one production project. It follows only ordinary methods that directly pass their parameters in order to a statically bound source method with an identical return type. Each member appears in call order in the finding evidence and related symbols, which makes changes to any participating source file select the finding in `changed-files`. The report prints the edge, type, and file counts and asks what responsibility each layer adds. It describes the statically declared chain in the loaded snapshot; it does not resolve runtime dispatch, claim that a layer is redundant, or measure historical growth. The analysis has no custom options. An audit with no candidates creates no analysis file. Analysis failure or cancellation publishes no run.

`missing-test-evidence-candidates` is enabled by default and reports explicit executable production C# functions that meet either `minDecisionCount` (default 3) or `minDecisionNesting` (default 2), and have no resolved path from a recognized static test root. When the only path goes through production code, the finding is labeled `indirect test path only` and additionally must meet either `minIndirectDecisionCount` (default 5) or `minIndirectDecisionNesting` (default 3), as well as the nontrivial gate. A direct path suppresses both categories. Each signal gives its category, measured decisions and nesting, and attribution uncertainty when applicable. An indirect-only finding includes one shortest resolved test-to-function path with stable symbol IDs and source locations, including source-generated intermediate functions. Uncertainty from an affected reachable method group or unresolved binding also marks its known downstream functions uncertain without adding a resolved path. The analysis uses the shared test-framework and control-flow contracts, does not execute tests, and cannot prove runtime coverage, assertion quality, or branch execution. Reflection, dependency injection, external tests, dynamic dispatch, and custom test discovery may hide paths. Its `changed-files` selection is snapshot-wide: no baseline shows all current findings; with a baseline, any added, changed, or deleted C# snapshot path shows all current findings, while an unchanged C# snapshot shows none. Non-C# changes do not select this analysis. `all-findings` always contains the complete current result, and all other analyses retain file-based selection. Its only options are the four positive integer thresholds and `enabled`; an audit with no candidates creates no analysis file, and failure or cancellation publishes no run.
`code-size-candidates` reports executable members, class and record-class symbols, and non-generated C# files from the loaded production-project snapshot. Members are selected by the configured nearest-rank size percentile plus the shared control-flow measurement, or independently by the extreme member threshold. Classes use aggregated partial declaration token-start lines and the corresponding percentile or extreme threshold. Files use loaded source line count or UTF-8 byte count. The compact signal prints the measured size, every selection path that fired, and the candidate-specific review question. A finding is a prompt for review, not a request to split code. Findings for a shared symbol are related to other analyses by symbol identity; changed-file selection includes every evidence file, including non-representative partial parts. The defaults and exact threshold ranges are in [Review configuration](../configuration/file-format.md).
