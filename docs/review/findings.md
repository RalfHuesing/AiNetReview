# Current findings

## Cyclic type dependency groups

`type-dependency-cycle-candidates` is enabled by default and reports one finding for each maximal strongly connected component in the production type graph with at least three distinct source types and at least three distinct canonical declaration files. These inclusive floors use all partial declarations; a shared source path linked into multiple projects counts once while project-specific type nodes remain distinct. Self-edges and repeated reference sites do not increase edge counts. Each finding lists every participating type declaration, every internal directed edge with its retained source witnesses, raw type/file/project/edge counts, and one deterministic genuine simple cycle as an illustrative witness. All component types are production finding subjects. Direct test references, generated or metadata types, dynamic targets, implicit compiler-created types, and guessed runtime dispatch are excluded.

## Dependency hubs

`type-dependency-hub-candidates` is enabled by default with independent positive integer options `minFanIn` and `minFanOut`, both defaulting to 10. It reports a production type only when both inclusive thresholds are met by distinct direct production neighbors. Repeated reference sites do not increase counts. Each finding exposes fan-in/fan-out, effective thresholds, distinct neighbor file/project counts in each direction, every direct production neighbor with retained edge witnesses, all partial declarations of the subject, and direct test consumers as separately labeled context. A finding has only the hub type as its subject; test consumers do not increase production counts or change its production origin. File counts deduplicate canonical project-root-relative paths, including linked files, while project counts keep project-specific nodes distinct. Generated, metadata, dynamic, implicit compiler-created types, and guessed runtime dispatch remain outside this static graph..

`IReviewAnalysis.ExecuteAsync` returns a `ReviewAnalysisResult` containing immutable `FindingDraft` values. A draft currently carries project and source paths, a subject ID, discriminator, starting line, rationale, numeric metrics, and evidence entries. It contains no snapshot, comparison text, fingerprint, or source-file hash list.

`ReviewRunner` invokes the configured analyses in ordinal analysis-ID order and returns each analysis's current result. It validates each draft against loaded C# project/document paths and source text, including one-based line bounds, finite metrics, required evidence, and unique per-run identity tuples. Findings are sorted deterministically and are not retained between calls. Invalid findings or analysis failures fail the run; cancellation returns no partial result. The reporting path derives map entries directly from validated findings without additional semantic map preparation.

Cross-analysis relationships match project path and symbol identity; sharing only a source file does not create a relationship. Related references retain the precise member path and line for clusters.

The same run result exposes a sorted classification for every loaded C# project, including projects with no findings. Each classification includes its role (`Production` or `Tests`) and the marker that determined that role: a test reference assembly, project name suffix, project-file name suffix, exact test path segment, or absence of a recognized test marker. Each built finding carries role-classified related symbols and separate subject occurrences that determine its report area. Evidence paths and test-path context remain available for precise source locations and cross-analysis relationships without changing a production finding into a test or mixed finding. Structural fragment occurrences retain distinct range identities even when multiple fragments share one owner and starting line. The classifier keeps its existing reference, suffix, and path rules, and generated-source exclusions are unchanged.

`MarkdownReportWriter` writes UTF-8 Markdown with LF line endings and atomically publishes the complete `production/`, `tests/`, and `mixed/` report areas with the root index and `audit-map/index.md`. Findings are assigned by subject occurrence role; contextual test evidence does not change finding origin. Maps group by representative project and source file, then list each canonical detail path once with all stable IDs routed there; map paths are relative to the map. Detailed reports are the canonical finding evidence: source paths are repository-relative, `Lnn` inherits the file heading, and structural ranges carry their own line positions. Related findings group IDs once per exact report-relative path. IDs derive deterministically from analysis and finding identity. Generated Markdown uses plain code-span paths, without Markdown links or HTML anchors. The root guidance covers investigation and evidence-based classification without requiring mechanical refactors.

Each nonempty analysis report shows its purpose, applicable effective options, review questions, exact finding total, representative project/file counts, and deterministic findings. Related cluster members, evidence files, and additional partial declarations do not increase representative counts. Every finding appears once in its area. Structural fragments and forwarding paths list every actual occurrence; missing-test-evidence path evidence retains test-role context while the finding remains production-origin. When every missing-test-evidence finding in a report has uncertain attribution, one shared header note explains the uncertainty; otherwise uncertainty is marked on affected findings. Questions guide investigation and do not prescribe mechanical changes. Analysis counting, temporary-directory publication, and older-run preservation follow the documented analysis contracts.


The production registry contains `code-size-candidates`, `method-control-flow-outliers`, `dead-code-candidates`, `duplicate-code-candidates`, `indirection-drift-candidates`, `missing-test-evidence-candidates`, `non-ascii-identifiers`, `structural-duplication-candidates`, `type-dependency-cycle-candidates`, and `type-dependency-hub-candidates`. `method-control-flow-outliers` compares executable method declarations within every C# project using separate project-relative populations. It uses the nearest-rank percentile selected by the `percentile` option (default 90), with minimum cutoffs of 8 decisions and 4 nested decisions. Test projects may override `percentile` through `testOptions`; omitted test values inherit the effective general option. Ties at the cutoff are included, so the report does not hide methods sharing a boundary value.

The analysis analyzes production and test C# projects using separate project-relative populations. Test projects use supported `testOptions` values when configured and otherwise inherit the effective general options. The shared Core source classifier identifies test projects from known test-framework reference assembly names (`xunit`, `nunit`, `mstest`, and Microsoft TestPlatform families), common project-name or project-file suffixes (`Tests`, `Test`, `UnitTests`, `UnitTest`, `IntegrationTests`, `IntegrationTest`, `FastTests`, `ComponentTests`, `TestKit`, `Specs`, and `Spec`), or exact test directory segments (`tests`, `test`, `unittests`, `integrationtests`, `fasttests`, `componenttests`, `testkit`, `specs`, and `spec`). Suffix matching requires a dotted or uppercase token boundary. These are deterministic conventions; an unusual test project without any of these markers is not inferred to be a test project.

Generated documents are excluded when their path is under `obj` or their filename ends in `.g.cs`, `.g.i.cs`, `.generated.cs`, or `.designer.cs`, or when one of the first five source lines contains `<auto-generated`. Methods are excluded when the method or a containing type has `GeneratedCodeAttribute` or `CompilerGeneratedAttribute`. The classifier reads source text only from the loaded Roslyn solution.

`decisionCount` counts each `if`, switch section (including `default` and grouped labels as one section), switch-expression arm, conditional expression, loop (`for`, `foreach`, `while`, or `do`), and `catch` clause once. `decisionConstructCount` counts each `if`, conditional expression, loop, and `catch` once, and counts an entire switch statement or switch expression once, regardless of its number of sections or arms. Boolean and null-coalescing operators (`&&`, `||`, and `??`) do not add decisions. `maxDecisionNesting` is the deepest nesting of counted decisions; an `else if` chain remains at the same nesting level. These structural measures are not cyclomatic complexity. Reports for `method-control-flow-outliers`, `code-size-candidates`, and `missing-test-evidence-candidates` include this counting note. A method is selected at inclusive cutoffs when `decisionCount` meets its effective cutoff **and** `decisionConstructCount` is at least 2, or when `maxDecisionNesting` meets its effective cutoff. Decision and nesting nearest-rank cutoffs are independent per project and floored at 8 and 4, respectively. This keeps a single flat switch from qualifying solely because it has many arms, while retaining methods with multiple separate decisions and deeply nested paths. `sourceSpanLines` gives the inclusive method declaration span as context, not as a selection threshold. Local functions and lambdas are not emitted as separate candidates or added to their containing method's counts.

Each finding includes the method symbol, declaration location, a source snippet identifying the deepest counted decision, raw metric values, project group size, percentile values, effective cutoffs, and descending ranks. The report signal shows the triggered decision or nesting values and their cutoffs. A finding is a review prompt, not a defect claim or a refactoring instruction. `FixtureFindingAnalysis` remains confined to IntegrationTests.

`dead-code-candidates` examines explicit types and ordinary methods in production and test C# projects. It accounts for solution-wide semantic references, recognized indirect bindings and the captured markup snapshot. A type with no known external use is reported once as a group, so its methods do not appear as separate findings. The actual compiler entry point and every containing type are protected in executable projects, including top-level entry points associated with an explicitly declared partial `Program`; ordinary unused methods in those types remain candidates. This protection uses the compilation's selected entry point and applies in both API modes. A library method named `Main` receives no compiler-entry-point protection. The default `apiSurface` value, `external_library`, protects publicly visible declarations in both project roles; `closed_solution` also considers them as candidates. `entryPointAttributes` adds fully qualified attribute type names while the built-in module initializer and JS interop entry point attributes stay active. Metadata-backed xUnit v2/v3, NUnit, and MSTest test methods, fixtures, lifecycle hooks and supported statically named data providers are protected, including inherited and explicitly skipped tests. Both the legacy Visual Studio Test Platform and current `MSTest.TestFramework` assembly identities are recognized. An unresolved data-provider type conservatively excludes the originating project and its referenced C# dependency area from candidate selection; the analysis result retains each excluded project path and reason for reporting. Ambiguous or statically unknown names on a known source type mark framework-plausible providers uncertain across that type and inherited members. This includes NUnit private static enumerable methods; ordinary void or scalar helpers remain candidates. Custom runners and unsupported data attributes are not claimed as resolved. Each finding identifies its declaration location and labels it as a type or method without known use. The report asks reviewers to check reflection, dependency injection, framework or markup entry points, and use outside the analyzed solution. Findings are recalculated on every audit; the analysis has no source-comment suppression mechanism. An audit with no candidates creates no analysis file. Analysis failure or cancellation publishes no run.

`duplicate-code-candidates` compares executable method, constructor, accessor, and local-function bodies in production and test C# projects using the loaded solution snapshot. Test and production methods share one comparison population, so a cluster may contain either or both project roles and may span projects. Bodies shorter than `minTokens` (default 30) are skipped. The fixed token algorithm preserves identifier and literal text, ignores whitespace and comments, creates deterministic five-token n-grams, and joins pairs that share at least three n-grams and meet the selected Jaccard threshold. `minimumSimilarity` defaults to `exact` (0.95); `near` (0.80) and `fuzzy` (0.65) are explicit lower thresholds. The report header maps all three presets and clarifies that `exact` names the strictest preset, not exact identity; similarity is Jaccard over distinct fixed five-token n-gram sets, ignoring whitespace/comments while retaining identifier/literal text without identifier or local-name normalization. One finding represents each connected cluster formed by qualifying edges and contains every member's project-relative source location, method identity, token count, and source-line evidence. Its score is the lowest qualifying edge score in that cluster. Members may come from different projects. Report rows show the cluster size and similarity relative to the selected minimum and retain every member's location and identity. Similarity alone does not prove that methods should be merged. Clusters are recomputed for every audit; an audit with no candidates creates no analysis file. Analysis failure or cancellation publishes no run.

`structural-duplication-candidates` groups exact contiguous fragments of at least three sibling statements and 60 original non-trivia tokens across production and test C# source. It compares complete syntax structure and retained token values, normalizing only semantically bound local and parameter names with recursive nullable-aware type keys. It analyzes explicit ordinary methods, constructors, property/event accessors, and block-bodied local functions; nested local/lambda declarations and unresolved, ambiguous, or dynamic value/member bindings stop fragments in the enclosing owner. At least two distinct executable declarations must contribute. Groups are not joined by overlap, and a smaller finding is suppressed only when every occurrence is contained in a larger qualifying group. The report header explains that any additional uncontained occurrence can justify an overlapping smaller group. Its signal gives occurrence, executable, statement, and token counts and states that the fragment is identical after local/parameter normalization. The dedicated report branch emits every occurrence in deterministic order with separate project and source paths, owner identity, and one-based start and end-exclusive line/column positions. Its fixed explanation and review question appear once in the header. This bounded signal does not claim semantic equivalence or prescribe refactoring. It has only the standard `enabled` option; an audit without candidates creates no analysis file, and failure or cancellation publishes no run.

`non-ascii-identifiers` flags identifier tokens that contain non-ASCII characters in production and test C# source. It inspects namespaces, types (classes, records, structs, interfaces, and enums), enum members, methods, properties, fields, parameters, local functions, and local variables. Allowed characters for identifiers are `a-z`, `A-Z`, `0-9`, and underscore (namespaces additionally allow dot). Verbatim identifiers with an `@` prefix ignore the `@`. Generated code and symbols are excluded using the shared Core source classifier. Findings report the declaration's project and source paths, symbol identity, start line, and evidence pointing to the identifier token. The analysis supports only `enabled` (default `true`) without additional options. An audit with no candidates creates no analysis file. Analysis failure or cancellation publishes no run.

`indirection-drift-candidates` reports one candidate for each maximal root path containing at least two transparent forwarding edges, three distinct containing types, and three distinct project-relative C# source files within one project regardless of whether that project is production or test code. It follows only ordinary methods that directly pass their parameters in order to a statically bound source method in the same project with an identical return type. Each member appears in call order in the finding evidence and related symbols. The report prints the edge, type, and file counts and asks what responsibility each layer adds. It describes the statically declared chain in the loaded snapshot; it does not resolve runtime dispatch, claim that a layer is redundant, or measure historical growth. The analysis has no custom options. An audit with no candidates creates no analysis file. Analysis failure or cancellation publishes no run.

`missing-test-evidence-candidates` is enabled by default and reports explicit executable production C# functions that meet either `minDecisionCount` (default 3) or `minDecisionNesting` (default 2), and have no resolved path from a recognized static test root. When the only path goes through production code, the finding is labeled `indirect test path only` and additionally must meet either `minIndirectDecisionCount` (default 5) or `minIndirectDecisionNesting` (default 3), as well as the nontrivial gate. A direct path suppresses both categories. The report header states the two OR-based complexity gates and that a direct resolved static path suppresses a finding. The `attribution uncertain` marker means static test attribution may be incomplete; it can result from reachable unresolved bindings, method groups, or virtual/interface dispatch, and can propagate to downstream methods over known calls. Reachable global uncertainty can mark every function, so the marker alone does not mean that a test is missing or that each marked function itself has an unresolved binding. It does not assess test assertion quality. An indirect-only finding includes one shortest resolved test-to-function path with concise symbol identities and source locations, including source-generated intermediate functions. Uncertainty from an affected reachable method group or unresolved binding also marks its known downstream functions uncertain without adding a resolved path. The analysis uses the shared test-framework and control-flow contracts, does not execute tests, and cannot prove runtime coverage, assertion quality, or branch execution. Reflection, dependency injection, external tests, dynamic dispatch, and custom test discovery may hide paths. Its only options are the four positive integer thresholds and `enabled`; an audit with no candidates creates no analysis file, and failure or cancellation publishes no run.

The missing-test-evidence graph includes block and expression bodies of methods, constructors, accessors (including event and init accessors), properties, indexers, operators, and conversions in production and test projects. For expression bodies, outer parentheses and nullable-warning suppression (`!`) are transparent to semantic operation lookup; calls and accessor references in the operand retain their graph edges and test associations. A body whose semantic operation remains unavailable fails the analysis instead of silently dropping the function. Constructor initializer calls are collected separately.

`code-size-candidates` reports executable members, class and record-class symbols, and non-generated C# files from every loaded C# project role. Test projects may override its seven numeric options through `testOptions`; omitted test values inherit the effective general options. Member code lines count distinct physical source lines with non-missing C# token starts in the full executable declaration; comments and blank lines without tokens do not count, while signatures, attributes, and braces count where token starts occur. A multiline literal contributes its token-start line; continuation lines count only when another token starts there. Type code lines sum the same counts across non-generated parts of an explicit class or record class symbol, excluding nested types and delegates. File lines are physical source lines, and file bytes are UTF-8 bytes without a BOM. Members are selected when their code lines meet both the configured minimum and the project nearest-rank percentile and the fixed control-flow gate `(decisions >= 8 AND constructs >= 2) OR nesting >= 4`, or independently meet `extremeMemberCodeLines`. Types meet both the configured minimum and project percentile or independently meet `extremeTypeCodeLines`; files meet either `extremeFileLines` or `extremeFileUtf8Bytes`. The compact signal prints the measured size and every selection path that fired. Each candidate kind's review question appears once in the report header. A finding is a prompt for review, not a request to split code. Findings for a shared symbol are related to other analyses by symbol identity. The defaults and exact threshold ranges are in [Review configuration](../configuration/file-format.md).
