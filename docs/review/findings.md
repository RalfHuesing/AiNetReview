# Current findings

`IReviewAnalysis.ExecuteAsync` returns a `ReviewAnalysisResult` containing immutable `FindingDraft` values. A draft currently carries project and source paths, a subject ID, discriminator, starting line, rationale, numeric metrics, and evidence entries. It contains no snapshot, comparison text, fingerprint, or source-file hash list.

`ReviewRunner` invokes the configured analyses in ordinal analysis-ID order and returns each analysis's current result. It validates each draft against the loaded C# project and document paths and source text, including one-based line bounds, finite metrics, required evidence, and unique per-run identity tuples. A finding's representative source must belong to its declared project; evidence may point to any loaded C# document in the solution. Evidence snippets must occur on their referenced loaded snapshot line. Findings are sorted by project path, source path, start line, subject ID, and discriminator. It retains no result between calls. Review analysis exceptions and invalid findings fail the whole analysis; cancellation propagates without returning a partial result.

The host reads the optional `baseline.json` from the resolved output directory before running the analyses. `ReviewRunner` then adds per-finding review metadata while preserving each validated analysis result unchanged: participating source paths include the finding source and every evidence source; `changed-files` selection is true when any participating file is missing from the baseline or has a different SHA-256. With no baseline, every current source file is considered new. A duplicate-code cluster explicitly identifies each member symbol and source location, so a change to any member selects the cluster. Cross-analysis relationships match project path and symbol identity; sharing only a source file does not create a relationship. Related references retain the precise member path and line for clusters.

The same run result exposes a sorted classification for every loaded C# project, including projects with no findings. Each classification includes its existing role (`Production` or `Tests`) and the marker that determined that role: a test reference assembly, project name suffix, project-file name suffix, exact test path segment, or absence of a recognized test marker. Each built `ReviewFinding` also carries a role beside every represented symbol from its `FindingDraft.RelatedSymbols`. Structural fragment occurrences retain distinct range identities even when multiple fragments share one owner and starting line. Finding origin can therefore be derived from represented occurrences; evidence files alone do not change it. The classifier keeps its existing reference, suffix, and path rules, and generated-source exclusions are unchanged.

`MarkdownReportWriter` writes UTF-8 Markdown with LF line endings. The root `index.md` places review guidance before findings links and baseline instructions. It frames findings as potential signals that may suggest deeper or cross-cutting issues, but do not prove a defect or require a change. Reviewers first read applicable target repository instructions and relevant design documents, then investigate every finding in the commissioned working set using relevant source code, callers, contracts, and tests in the context of application goals, architecture, and responsibilities. Related findings may be evaluated together. Heuristic origin or uncertain attribution alone does not justify dismissing a signal. Every classification requires concrete evidence: false positive, acceptable design, needs clarification, or actionable. An accurate signal can describe an acceptable design; it is distinct from a false positive. Changes follow from this assessment rather than from a signal alone. The guidance discourages metric-driven refactoring and symptom workarounds, allows locally scoped changes when justified by the broader context, asks agents to explain consequential changes and tradeoffs, and presents drift prevention as a goal rather than a proven analysis result. `changed-files/` is the primary working set; the root index and every standalone report in `all-findings/` explicitly require a user request for a full repository audit before those findings are inspected or reported. Standalone analysis reports state the investigation and classification requirement within the commissioned scope and link back to the root guidance. A normal CLI run prints the PowerShell baseline command `<exePath> baseline "<projectRoot>"`, using the `ainetreview.json` and output directory configured in that project root. A centrally hosted manual audit instead prints a command to run `scripts/test-audit.ps1 -Target <name> -BaselineOnly`, which refreshes the central baseline from the selected host-side audit profile without writing config or baseline files to the target repository. Each view has its own `index.md` linking only to analysis files that contain findings in that view; `all-findings/index.md` includes an explicit notice instructing AI agents not to process findings from that view unless requested. With no baseline, every current source file is considered new, so both views contain the same findings. An active audit with no findings says `No findings were found`; an audit with no active analyses says `No review was performed because all analyses are disabled`. Empty views do not create analysis files.

Each nonempty analysis report shows its purpose, view-specific review policy, effective options, review questions, a `## Summary` with the exact finding total and project/source-file counts, then a `## Findings` section. Project headings include file and finding counts; file headings include finding counts, so a duplicate summary table is unnecessary. Findings are grouped unconditionally by their representative `(projectPath, sourcePath)` pair, with projects and files in ordinal order and each group's findings ordered by start line, subject ID, and discriminator. Cluster members, partial declarations, forwarding members, and evidence in other files do not add group counts. Every finding still appears once as an individual item. Ordinary findings display their one-based representative start line. Cluster and forwarding member locations include their one-based lines; shortest indirect test paths retain each evidence location and render each full symbol ID and `Source:line` in separate safe code spans. `structural-duplication-candidates` lists every fragment occurrence with its project, file, owner identity, and one-based start/end-exclusive coordinates; its explanation and review question appear once in the header. Code-size review questions appear once per candidate kind in the header; findings retain their signal kind, concrete measurements, and selection reasons, describing relative selection rules as criteria and independent cutoffs as thresholds. The method-control-flow, code-size, and missing-test-evidence reports include a shared counting note: `decisionCount` counts each `if`, conditional expression, loop, and `catch` once, and each switch section or switch-expression arm once; `decisionConstructCount` counts each of those `if`/conditional/loop/`catch` constructs once and each whole switch once. Nesting is the maximum depth of counted decisions, with `else if` chains at the same depth. `&&`, `||`, and `??` do not add decisions; these counts are not cyclomatic complexity. Missing-test-evidence reports explain that `attribution uncertain` marks a potentially incomplete static test association, may come from reachable unresolved bindings, method groups, or virtual/interface dispatch, and can propagate over known calls; it does not assess assertion quality. Its `changed-files` report explains the snapshot-wide selection and, once per representative file group, states whether that source itself is new/changed or unchanged while included snapshot-wide. Output escapes Markdown headings, code spans, item content, and index links, including backticks, brackets, Unicode, and newlines. Output omits HTML anchors, source hyperlinks, raw metrics, long rationale text, and code snippets. Related-analysis suffixes refer to visibility in the complete current view, not only the current analysis report. The `changed-files/` reports are independent copies, so editing them does not modify the complete `all-findings/` view. Analyses, findings, options, groups, and evidence have deterministic ordering. Each report set, including both views and indexes, is assembled in a unique temporary directory and published by renaming that directory to its UTC timestamp and random run ID. After a pre-publication failure, the writer makes bounded attempts to remove its temporary directory. A persistent file lock can leave a clearly named temporary directory; successful runs leave older reports unchanged.

The production registry contains `code-size-candidates`, `method-control-flow-outliers`, `dead-code-candidates`, `duplicate-code-candidates`, `indirection-drift-candidates`, `missing-test-evidence-candidates`, `non-ascii-identifiers`, and `structural-duplication-candidates`. `method-control-flow-outliers` compares executable method declarations within every C# project using separate project-relative populations. It uses the nearest-rank percentile selected by the `percentile` option (default 90), with minimum cutoffs of 8 decisions and 4 nested decisions. Test projects may override `percentile` through `testOptions`; omitted test values inherit the effective general option. Ties at the cutoff are included, so the report does not hide methods sharing a boundary value.

The analysis analyzes production and test C# projects using separate project-relative populations. Test projects use supported `testOptions` values when configured and otherwise inherit the effective general options. The shared Core source classifier identifies test projects from known test-framework reference assembly names (`xunit`, `nunit`, `mstest`, and Microsoft TestPlatform families), common project-name or project-file suffixes (`Tests`, `Test`, `UnitTests`, `UnitTest`, `IntegrationTests`, `IntegrationTest`, `FastTests`, `ComponentTests`, `TestKit`, `Specs`, and `Spec`), or exact test directory segments (`tests`, `test`, `unittests`, `integrationtests`, `fasttests`, `componenttests`, `testkit`, `specs`, and `spec`). Suffix matching requires a dotted or uppercase token boundary. These are deterministic conventions; an unusual test project without any of these markers is not inferred to be a test project.

Generated documents are excluded when their path is under `obj` or their filename ends in `.g.cs`, `.g.i.cs`, `.generated.cs`, or `.designer.cs`, or when one of the first five source lines contains `<auto-generated`. Methods are excluded when the method or a containing type has `GeneratedCodeAttribute` or `CompilerGeneratedAttribute`. The classifier reads source text only from the loaded Roslyn solution.

`decisionCount` counts each `if`, switch section (including `default` and grouped labels as one section), switch-expression arm, conditional expression, loop (`for`, `foreach`, `while`, or `do`), and `catch` clause once. `decisionConstructCount` counts each `if`, conditional expression, loop, and `catch` once, and counts an entire switch statement or switch expression once, regardless of its number of sections or arms. Boolean and null-coalescing operators (`&&`, `||`, and `??`) do not add decisions. `maxDecisionNesting` is the deepest nesting of counted decisions; an `else if` chain remains at the same nesting level. These structural measures are not cyclomatic complexity. Reports for `method-control-flow-outliers`, `code-size-candidates`, and `missing-test-evidence-candidates` include this counting note. A method is selected at inclusive cutoffs when `decisionCount` meets its effective cutoff **and** `decisionConstructCount` is at least 2, or when `maxDecisionNesting` meets its effective cutoff. Decision and nesting nearest-rank cutoffs are independent per project and floored at 8 and 4, respectively. This keeps a single flat switch from qualifying solely because it has many arms, while retaining methods with multiple separate decisions and deeply nested paths. `sourceSpanLines` gives the inclusive method declaration span as context, not as a selection threshold. Local functions and lambdas are not emitted as separate candidates or added to their containing method's counts.

Each finding includes the method symbol, declaration location, a source snippet identifying the deepest counted decision, raw metric values, project group size, percentile values, effective cutoffs, and descending ranks. The report signal shows the triggered decision or nesting values and their cutoffs. A finding is a review prompt, not a defect claim or a refactoring instruction. `FixtureFindingAnalysis` remains confined to IntegrationTests.

`dead-code-candidates` examines explicit types and ordinary methods in production C# projects. It accounts for solution-wide semantic references, recognized indirect bindings and the captured markup snapshot. A type with no known external use is reported once as a group, so its methods do not appear as separate findings. The actual compiler entry point and every containing type are protected in executable projects, including top-level entry points associated with an explicitly declared partial `Program`; ordinary unused methods in those types remain candidates. This protection uses the compilation's selected entry point and applies in both API modes. A library method named `Main` receives no compiler-entry-point protection. The default `apiSurface` value, `external_library`, protects publicly visible declarations; `closed_solution` also considers them as candidates. `entryPointAttributes` adds fully qualified attribute type names while the built-in module initializer and JS interop entry point attributes stay active. Each report row links to its declaration and labels it as a type or method without known use. The report asks reviewers to check reflection, dependency injection, framework or markup entry points, and use outside the analyzed solution. Findings are recalculated on every audit; the analysis has no source-comment suppression mechanism. An audit with no candidates creates no analysis file. Analysis failure or cancellation publishes no run.

`duplicate-code-candidates` compares executable method, constructor, accessor, and local-function bodies in production and test C# projects using the loaded solution snapshot. Test and production methods share one comparison population, so a cluster may contain either or both project roles and may span projects. Bodies shorter than `minTokens` (default 30) are skipped. The fixed token algorithm preserves identifier and literal text, ignores whitespace and comments, creates deterministic five-token n-grams, and joins pairs that share at least three n-grams and meet the selected Jaccard threshold. `minimumSimilarity` defaults to `exact` (0.95); `near` (0.80) and `fuzzy` (0.65) are explicit lower thresholds. The report header maps all three presets and clarifies that `exact` names the strictest preset, not exact identity; similarity is Jaccard over distinct fixed five-token n-gram sets, ignoring whitespace/comments while retaining identifier/literal text without identifier or local-name normalization. One finding represents each connected cluster formed by qualifying edges and contains every member's project-relative source location, method identity, token count, and linked source-line evidence. Its score is the lowest qualifying edge score in that cluster. Members may come from different projects. Report rows show the cluster size and similarity relative to the selected minimum, and link to every member. Similarity alone does not prove that methods should be merged. Clusters are recomputed for every audit; an audit with no candidates creates no analysis file. Analysis failure or cancellation publishes no run.

`structural-duplication-candidates` groups exact contiguous fragments of at least three sibling statements and 60 original non-trivia tokens across production and test C# source. It compares complete syntax structure and retained token values, normalizing only semantically bound local and parameter names with recursive nullable-aware type keys. It analyzes explicit ordinary methods, constructors, property/event accessors, and block-bodied local functions; nested local/lambda declarations and unresolved, ambiguous, or dynamic value/member bindings stop fragments in the enclosing owner. At least two distinct executable declarations must contribute. Groups are not joined by overlap, and a smaller finding is suppressed only when every occurrence is contained in a larger qualifying group. The report header explains that any additional uncontained occurrence can justify an overlapping smaller group. Its signal gives occurrence, executable, statement, and token counts and states that the fragment is identical after local/parameter normalization. The dedicated report branch emits every occurrence in deterministic order with separate project and source paths, owner identity, and one-based start and end-exclusive line/column positions. Its fixed explanation and review question appear once in the header. This bounded signal does not claim semantic equivalence or prescribe refactoring. It has only the standard `enabled` option; an audit without candidates creates no analysis file, and failure or cancellation publishes no run.

`non-ascii-identifiers` flags identifier tokens that contain non-ASCII characters in production and test C# source. It inspects namespaces, types (classes, records, structs, interfaces, and enums), enum members, methods, properties, fields, parameters, local functions, and local variables. Allowed characters for identifiers are `a-z`, `A-Z`, `0-9`, and underscore (namespaces additionally allow dot). Verbatim identifiers with an `@` prefix ignore the `@`. Generated code and symbols are excluded using the shared Core source classifier. Findings report the declaration's project and source paths, symbol identity, start line, and evidence pointing to the identifier token. The analysis supports only `enabled` (default `true`) without additional options. An audit with no candidates creates no analysis file. Analysis failure or cancellation publishes no run.

`indirection-drift-candidates` reports one candidate for each maximal root path containing at least two transparent forwarding edges, three distinct containing types, and three distinct project-relative C# source files within one project regardless of whether that project is production or test code. It follows only ordinary methods that directly pass their parameters in order to a statically bound source method in the same project with an identical return type. Each member appears in call order in the finding evidence and related symbols, which makes changes to any participating source file select the finding in `changed-files`. The report prints the edge, type, and file counts and asks what responsibility each layer adds. It describes the statically declared chain in the loaded snapshot; it does not resolve runtime dispatch, claim that a layer is redundant, or measure historical growth. The analysis has no custom options. An audit with no candidates creates no analysis file. Analysis failure or cancellation publishes no run.

`missing-test-evidence-candidates` is enabled by default and reports explicit executable production C# functions that meet either `minDecisionCount` (default 3) or `minDecisionNesting` (default 2), and have no resolved path from a recognized static test root. When the only path goes through production code, the finding is labeled `indirect test path only` and additionally must meet either `minIndirectDecisionCount` (default 5) or `minIndirectDecisionNesting` (default 3), as well as the nontrivial gate. A direct path suppresses both categories. Each signal gives its category, measured decisions and nesting, and attribution uncertainty when applicable. The report header states the two OR-based complexity gates and that a direct resolved static path suppresses a finding. The `attribution uncertain` marker means static test attribution may be incomplete; it can result from reachable unresolved bindings, method groups, or virtual/interface dispatch, and can propagate to downstream methods over known calls. Reachable global uncertainty can mark every function, so the marker alone does not mean that a test is missing or that each marked function itself has an unresolved binding. It does not assess test assertion quality. An indirect-only finding includes one shortest resolved test-to-function path with stable symbol IDs and source locations, including source-generated intermediate functions. Uncertainty from an affected reachable method group or unresolved binding also marks its known downstream functions uncertain without adding a resolved path. The analysis uses the shared test-framework and control-flow contracts, does not execute tests, and cannot prove runtime coverage, assertion quality, or branch execution. Reflection, dependency injection, external tests, dynamic dispatch, and custom test discovery may hide paths. Its `changed-files` selection is snapshot-wide because changes to test roots or the call graph can alter associations in unchanged production files: without a baseline, every current source file is treated as new; with a baseline, any added, changed, or deleted C# snapshot path shows all current findings, while an unchanged C# snapshot shows none. The changed-files report labels only each finding group's representative source file as new/changed or unchanged; unchanged means the file matches the baseline, not that the finding is unaffected. Non-C# changes do not select this analysis. `all-findings` always contains the complete current result, and all other analyses retain file-based selection. Its only options are the four positive integer thresholds and `enabled`; an audit with no candidates creates no analysis file, and failure or cancellation publishes no run.

The missing-test-evidence graph includes block and expression bodies of methods, constructors, accessors (including event and init accessors), properties, indexers, operators, and conversions in production and test projects. For expression bodies, outer parentheses and nullable-warning suppression (`!`) are transparent to semantic operation lookup; calls and accessor references in the operand retain their graph edges and test associations. A body whose semantic operation remains unavailable fails the analysis instead of silently dropping the function. Constructor initializer calls are collected separately.

`code-size-candidates` reports executable members, class and record-class symbols, and non-generated C# files from every loaded C# project role. Test projects may override its seven numeric options through `testOptions`; omitted test values inherit the effective general options. Member code lines count distinct physical source lines with non-missing C# token starts in the full executable declaration; comments and blank lines without tokens do not count, while signatures, attributes, and braces count where token starts occur. A multiline literal contributes its token-start line; continuation lines count only when another token starts there. Type code lines sum the same counts across non-generated parts of an explicit class or record class symbol, excluding nested types and delegates. File lines are physical source lines, and file bytes are UTF-8 bytes without a BOM. Members are selected when their code lines meet both the configured minimum and the project nearest-rank percentile and the fixed control-flow gate `(decisions >= 8 AND constructs >= 2) OR nesting >= 4`, or independently meet `extremeMemberCodeLines`. Types meet both the configured minimum and project percentile or independently meet `extremeTypeCodeLines`; files meet either `extremeFileLines` or `extremeFileUtf8Bytes`. The compact signal prints the measured size and every selection path that fired. Each candidate kind's review question appears once in the report header. A finding is a prompt for review, not a request to split code. Findings for a shared symbol are related to other analyses by symbol identity; changed-file selection includes every evidence file, including non-representative partial parts. The defaults and exact threshold ranges are in [Review configuration](../configuration/file-format.md).
